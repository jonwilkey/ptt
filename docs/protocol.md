# Wire protocol — milestone 2 (enrollment and paging)

This is the wire-format contract shared by the Go server (`pttd`) and the Android app for
milestone 2: enrollment and paging. It covers the REST API, the page state machine, and the
FCM data messages. Where this document lists more than [`spec.md`](spec.md) (for example the FCM
message list in §9), it **extends** the spec; the spec remains authoritative for everything this
document does not cover.

**Scope.** This document covers enrollment and paging only. The in-app-update endpoints
(`GET /v1/app/latest`, `GET /v1/app/apk/<version>`) are defined in the spec but omitted here.
Test devices and two pre-provisioned test accounts are server-side details; they never appear in
`GET /v1/contacts` or in the family roster, and this document does not give them a wire form.

## Privacy

No log line, metric label, or `audit_log` row records a page id, session id, sender, or
recipient. The audit log covers enrollment, revocation, roster changes, and authentication
failures only.

## 1. Encodings

| Item | Encoding |
| --- | --- |
| Binary in JSON (keys, signatures, tokens, codes, secrets) | base64url **without** padding (RFC 4648 §5); called **b64u** |
| Timestamps | integer unix **milliseconds**, UTC |
| IDs (user, device, page, session) | lowercase canonical UUID, 36 characters |
| Character set | UTF-8 |

`user_id` is assigned by the server; `device_id`, `page_id`, and `session_id` are generated by
the phone.

Decoders are strict: b64u values are rejected if padded or in the standard alphabet (Go
`base64.RawURLEncoding.Strict()`), and an ID that is not a canonical lowercase UUID is
`invalid_request` — the HPKE `info` input and the enrollment MAC both rely on fixed-length IDs.

### Errors

Every error is an HTTP status plus a JSON body of exactly one field:

```json
{"error": "<code>"}
```

| Code | Status | Meaning |
| --- | --- | --- |
| `invalid_request` | 400 | Body malformed or a field invalid |
| `unauthorized` | 401 | Missing/unknown device token, or no auth where a token is required |
| `forbidden` | 403 | Authenticated but not allowed (e.g. a non-admin on an admin endpoint) |
| `not_found` | 404 | No such resource |
| `method_not_allowed` | 405 | Right resource, wrong method |
| `conflict` | 409 | State conflict (see endpoints) |
| `code_invalid` | 400 | Enrollment code unknown, already used, or expired — **one code for all three** |
| `roster_invalid` | 400 | Roster signature, format, or content rejected |
| `roster_stale` | 409 | Roster version is not higher than the current one |
| `already_answered` | 409 | `answer` on a page another device already answered |
| `page_ended` | 410 | Any action on a page that has ended (except `cancel` → `204`) |
| `rate_limited` | 429 | Too many requests; `Retry-After` header in seconds |

`code_invalid` deliberately gives no oracle: the server does not distinguish unknown, used, and
expired codes.

### Rate limits

| Endpoint | Limit |
| --- | --- |
| `POST /v1/enroll` | 5 / hour, per client IP |
| `POST /v1/pages` | 30 / minute, per device |

## 2. Secrets and keys

| Item | Generation | Where it lives |
| --- | --- | --- |
| Device token | 32 random bytes | App only; server stores **SHA-256** |
| Enrollment code | 16 random bytes | App QR + server (server stores **SHA-256**) |
| Enrollment secret | 32 random bytes | **Admin phone + QR only** — never sent to the server |
| Ed25519 signing key | per device | Phone (secret); public key in the roster |
| X25519 HPKE key | per device | Phone (secret); public key in the roster |

- **Device token.** Sent as `Authorization: Bearer <token>`, where `<token>` is the token b64u
  (43 characters). The server stores only `SHA-256(token)`; a leaked database does not yield a
  usable token.
- **Enrollment code.** The QR carries it b64u (22 characters). The `code_id` in a URL is
  `b64u(SHA-256(code bytes))` — a public, non-secret handle.
- **Enrollment secret.** Generated by the admin phone, present only in the QR. It is the key for
  the enrollment MAC in §5.
- **Device keys.** A fresh Ed25519 and a fresh X25519 key pair per device. Public keys are the
  raw 32-byte keys, b64u (43 characters). Signatures are raw RFC 8032 (64 bytes, b64u = 86
  characters). Both Tink keysets use the **RAW** output prefix: `ED25519_RAW` for signing (the
  default `ED25519` template prefixes signatures with 5 bytes) and
  `DHKEM_X25519_HKDF_SHA256_HKDF_SHA256_CHACHA20_POLY1305_RAW` for HPKE. An HPKE-wrapped key is
  exactly `enc(32) || ct(32+16)` = 80 bytes.

## 3. Signed objects

The roster and the page envelope travel as a **signed object** — a JSON envelope whose `payload`
is opaque bytes and whose `sig` is computed over those bytes:

```json
{
  "payload": "<b64u(payload bytes)>",
  "signer": "<device id>",
  "sig": "<b64u(signature)>"
}
```

- `payload` — the exact UTF-8 JSON serialization of the payload object. `sig` is computed over
  these **exact bytes**; there is no canonical-JSON step.
- `sig` = `Ed25519_sign(signer's secret key, ctx || 0x00 || payload bytes)`, where `ctx` is the
  ASCII context string and `0x00` is a single separator byte.
- A verifier checks the signature over the received bytes **before** parsing `payload`. Parsing a
  tampered or malformed `payload` is a `roster_invalid` (roster) or a dropped message (envelope),
  not a parse crash.

Context strings:

| Context string | Used for |
| --- | --- |
| `ptt-roster-v1` | Family roster (signer: an admin device) |
| `ptt-envelope-v1` | Page envelope (signer: the sender device) |

## 4. Family roster

Payload object (the JSON that is b64u'd into a signed object's `payload`), signed with context
`ptt-roster-v1`:

```json
{
  "format": 1,
  "version": 7,
  "issued_at": 1789920000000,
  "devices": [
    {
      "id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
      "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
      "display_name": "Alex",
      "device_name": "Alex's phone",
      "admin": true,
      "ed25519": "<43 chars>",
      "x25519": "<43 chars>"
    }
  ]
}
```

- `format` — currently `1`; bump only for a payload-shape change.
- `version` — monotonic; a phone accepts a roster only if it is higher than the one it holds.
- `devices` — sorted by `id`; `id` is unique within a roster.
- `display_name` — the **person**; `device_name` — the **phone**. `admin` mirrors the user's
  `is_admin`.

**A phone accepts a roster only if** (in order):

1. the signature verifies under `ptt-roster-v1`;
2. the `signer` is an **admin** device in the phone's *current* roster — at enrollment, one of the
   QR's admin keys; for the bootstrap phone, its own key;
3. `version` is higher than the current one.

**The server accepts `PUT /v1/roster` only if**:

- the signature verifies under `ptt-roster-v1`;
- the `signer` is a non-revoked admin device in the server's current roster. If no roster exists
  yet, the signer's user is an admin **and** the roster lists the signer as an admin;
- `version` is higher than the current one (else `roster_stale`);
- every listed device exists on the server, is not revoked, and its `user_id`, Ed25519 key,
  X25519 key, and `admin` flag (= the user's `is_admin`) all match the server's records.

A device enrolled via a code but not yet listed in a roster is allowed (pending approval).
Omitting a device from a roster does **not** revoke it — revocation is the explicit
`POST /v1/devices/{id}/revoke`.

## 5. Enrollment

The QR encodes, as `pttenroll1:` followed by b64u(JSON):

```json
{
  "url": "https://ptt.example.com",
  "code": "<22 chars>",
  "secret": "<43 chars>",
  "admins": [
    { "id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57", "ed25519": "<43 chars>" }
  ]
}
```

Bootstrap QRs (`pttd admin bootstrap`) omit `secret` and `admins`.

**MAC** (admin enrollments only):

```
MAC = HMAC-SHA256(
        secret,
        "ptt-enroll-mac-v1" || 0x00 || code(16 bytes)
          || device_id(36 ASCII) || ed25519_pub(32) || x25519_pub(32)
      )
```

`code` is the raw 16 code bytes; `device_id` is the 36 ASCII characters of the UUID; the two
public keys are the raw 32-byte keys. The MAC is 32 bytes (b64u = 43 characters). Bootstrap
enrollments send no MAC.

**Flow:**

1. Admin phone `POST /v1/enrollment-codes` — gets a `code`, `code_id`, `expires_at`.
2. Admin phone shows the QR (URL + code + secret + the admin device ids/keys).
3. New phone generates its key pair and `device_id`, `POST /v1/enroll`s, and stores the returned
   device token.
4. Admin phone polls `GET /v1/enrollment-codes/{code_id}` every 2 s until `used`, verifies the
   returned `mac` against the MAC it computes with its own secret, and also checks the
   response's `admin` (== the `make_admin` it requested), `display_name` (== the name it
   requested), and `user_id` (== the `user_id` it requested, or, for a new person, a user id
   not already in its current roster) — otherwise it refuses to sign (this stops a malicious
   server attaching a phone to the wrong person or making it an admin). It then signs roster
   `version+1` that includes the new device (context `ptt-roster-v1`) and `PUT /v1/roster`.
5. Server sends an FCM `roster` message to all non-revoked devices (see §9).
6. New phone `GET /v1/roster` and verifies it: the signer must be one of the QR's admin keys, the
   roster must list that admin with the same key, and it must list the new phone itself with its
   own keys. Only then is the phone usable.

Enrolling (including re-enrolling after `pttd admin bootstrap --reset`) discards any earlier
local roster, so the version check starts over from the first roster accepted this way.

**Bootstrap phone:** after enrolling, it signs roster **version 1** containing only itself and
`PUT /v1/roster`s it — becoming the first admin.

## 6. REST endpoints

All bodies and responses are JSON. Authentication is `Authorization: Bearer <token>` (device
token) except `POST /v1/enroll` and `GET /healthz`, which are unauthenticated. Admin endpoints
require the caller's **user** to be an admin.

| Endpoint | Auth |
| --- | --- |
| `POST /v1/enrollment-codes` | admin |
| `GET /v1/enrollment-codes/{code_id}` | admin |
| `POST /v1/enroll` | none (rate-limited) |
| `PUT /v1/devices/me` | device |
| `POST /v1/devices/{id}/revoke` | admin |
| `GET /v1/contacts` | device |
| `GET /v1/roster` | device |
| `PUT /v1/roster` | admin |
| `POST /v1/pages` | device (rate-limited) |
| `POST /v1/pages/{id}/delivered` | device in envelope |
| `POST /v1/pages/{id}/acknowledge` | device in envelope |
| `POST /v1/pages/{id}/answer` | device in envelope |
| `POST /v1/pages/{id}/cancel` | sender (and answering device after an answer) |
| `GET /healthz` | none |

### `POST /v1/enrollment-codes` (admin)

```json
{ "display_name": "Alex", "make_admin": false, "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845" }
```

`user_id` adds the new device to an existing person; omit it to create a new person at enroll.
`display_name` is required unless `user_id` is given. With `user_id`, the code inherits that
user's `display_name` and `is_admin`; a `make_admin` that differs → `400 invalid_request` (omitted = inherit).
→ `201`

```json
{ "code": "<22 chars>", "code_id": "<22 chars>", "expires_at": 1789920000000 }
```

Codes expire after 24 hours.

### `GET /v1/enrollment-codes/{code_id}` (admin)

→ `200`

```json
{
  "status": "used",
  "device": {
    "id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
    "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
    "display_name": "Alex",
    "device_name": "Alex's phone",
    "admin": false,
    "ed25519": "<43 chars>",
    "x25519": "<43 chars>",
    "mac": "<43 chars>"
  }
}
```

`status` is `pending` | `used` | `expired`; `device` is present only when `used`. Once the
nightly cleanup has deleted the code → `404 not_found`.

### `POST /v1/enroll` (none)

```json
{
  "code": "<22 chars>",
  "device_id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
  "device_name": "Alex's phone",
  "ed25519": "<43 chars>",
  "x25519": "<43 chars>",
  "mac": "<43 chars>",
  "fcm_token": "<FCM token>",
  "app_version": "0.2.0"
}
```

`mac` is required for codes created by an admin phone and must be absent for bootstrap codes
(otherwise `400 invalid_request`). An existing `device_id` → `409 conflict`. The body is fully
validated before the code is consumed, and the code is consumed atomically with creating the
device.

→ `201`

```json
{
  "token": "<43 chars>",
  "device_id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
  "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
  "display_name": "Alex",
  "admin": false
}
```

### `PUT /v1/devices/me` (device)

```json
{
  "fcm_token": "<FCM token>",
  "app_version": "0.2.0",
  "device_name": "Alex's phone",
  "checklist": { "battery_ok": false }
}
```

All fields optional; absent fields are unchanged. A `false` checklist item drives the `warning`
presence in `GET /v1/contacts`. → `204`.

### `POST /v1/devices/{id}/revoke` (admin)

→ `204`, idempotent. The phone flow for removing a device is: sign and `PUT` a roster without the
device, **then** revoke it.

### `GET /v1/contacts` (device)

→ `200`

```json
{
  "users": [
    { "id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845", "display_name": "Alex", "admin": true, "presence": "ok" }
  ]
}
```

Only users with at least one non-revoked, non-test device are listed (so people orphaned by
`bootstrap --reset` disappear until they re-enroll). `presence` is `ok` | `warning` | `offline`. A user is `offline` if none of their non-revoked
devices has been seen in 48 h; otherwise `warning` if any device's latest checklist has a `false`
item; otherwise `ok`.

### `GET /v1/roster` (device)

→ `200` the signed object (§3) from §4, or `404 not_found` if none exists.

### `PUT /v1/roster` (admin)

Body is the signed object (§3) from §4. → `204` on success; `400 roster_invalid` / `409
roster_stale` otherwise.

### `POST /v1/pages` (device)

```json
{
  "id": "5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13",
  "to": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
  "level": "urgent",
  "session_id": "a8d4e6b2-71c9-4f30-8b5e-2c9a1d7e3f60",
  "envelope": { "payload": "<b64u>", "signer": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57", "sig": "<b64u>" }
}
```

`envelope` is a signed object (§3) whose payload is the page envelope (§7). → `201`

```json
{ "id": "5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13", "state": "ringing" }
```

- Same `id` + same body → `200` with the current state (idempotent retry).
  “Same body” means `to`, `level`, and `session_id` are equal, and the decoded envelope fields
  `payload`, `signer`, and `sig` are byte-equal. Idempotent retries do not count against the
  client's rate limit.
- Same `id` after the page has ended → `200` with `{"id":"5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13","state":"ended"}`; the server
  **never re-pushes** it.
- Same `id` with a different body → `409 conflict`.
- If none of the devices in `keys` is non-revoked, the page fails at once → `201
  {"id","state":"ended"}` and it is tombstoned; no `page_state` push is sent.
- Paging your own user is allowed (Test alert).

### `POST /v1/pages/{id}/delivered` · `/acknowledge` · `/answer`

Only a device listed in the envelope's `keys` may call these; any other caller → `403
forbidden`. Repeats are idempotent (`204`). `answer` after another
device has answered → `409 already_answered`. Unknown `id` with no tombstone → `404
not_found`; a tombstoned page → `410 page_ended` (except `cancel`, below). For **every** page
action the client's outbox treats `2xx`, `410 page_ended`, and `409 already_answered` as final
and deletes the row.

### `POST /v1/pages/{id}/cancel`

The sender may call it any time; after an answer, the answering device may too (this is the
"End" on the answer screen). Any other caller → `403 forbidden`; unknown `id` with no tombstone
→ `404 not_found`. → `204`, idempotent — including on a **tombstoned** page (it is already over,
and `cancel` is final).

### `GET /healthz`

Unchanged from the spec (liveness probe).

## 7. Page envelope

Payload object signed with context `ptt-envelope-v1` by the **sender** device:

```json
{
  "format": 1,
  "page_id": "5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13",
  "session_id": "a8d4e6b2-71c9-4f30-8b5e-2c9a1d7e3f60",
  "from_device": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
  "to_user": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
  "level": "normal",
  "created_at": 1789920000000,
  "keys": {
    "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57": "<b64u(HPKE enc || ciphertext)>"
  }
}
```

- `keys` maps each **recipient device id** to the HPKE-encryption of a 32-byte **session key**
  for that device. The sender wraps the key for exactly the devices in its current verified
  roster (§4) whose `user_id` is `to` — never from the server's contacts list.
- **HPKE** (RFC 9180) base mode: `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`,
  `ChaCha20-Poly1305`. Plaintext is the 32-byte session key. `info` =
  `"ptt-session-key-v1" || 0x00 || page_id || session_id || recipient device_id` (all ASCII).
  AAD is empty — Tink `HybridEncrypt` `contextInfo` = `info`. The keyset uses the
  `DHKEM_X25519_HKDF_SHA256_HKDF_SHA256_CHACHA20_POLY1305_RAW` template (RAW output prefix),
  so a wrapped key is exactly `enc(32) || ct(32+16)` = 80 bytes (b64u = 108 characters).

**Server** (never decrypts): parses the payload (not the signature) and rejects with
`invalid_request` unless the envelope's `signer` and the payload's `from_device` both equal the
caller's device id, `page_id`, `session_id`, `to_user`, and `level` equal the request's `id`,
`session_id`, `to`, and `level`, `keys` is non-empty, and every device id in `keys` is a device
of `to`. Entries for revoked devices are ignored, not pushed; the server pushes to the
non-revoked devices in `keys`, and if none remain the page ends as `failed`.

**Receivers:** verify the signature with `from_device`'s Ed25519 key from their own verified
roster, then check that `page_id` and `level` equal the push fields, that `to_user` is their
own user, that their own device id is in `keys`, that `from_device` is in the roster, and that
`from_user` equals that roster entry's `user_id` — dropping the message on signature failure or
any failed check. HPKE-decrypt their `keys` entry for the session key. The caller name shown
to the user comes from the roster entry, never from the server.

## 8. Page states and timers

Server-side states:

```
ringing ──▶ acknowledged (optional) ──▶ answered
```

A page is then **deleted** ("ended") on cancel, on missed, on failed, or on answered-page expiry.
`delivered_at` is a **flag**, not a state.

| Timer | Value |
| --- | --- |
| No `delivered` within | 30 s → re-push and tell the sender `not_delivered`; re-push again at 2 min |
| Normal page unanswered (acked or not) | 15 min → **missed** |
| Urgent page | **never** times out |
| Answered page | deleted **15 min** after the answer (milestone-2 stand-in for the milestone-4 session) |

- Ended pages leave a **tombstone** (id only) for **24 h**, so a late idempotent `POST /v1/pages`
  returns `ended`, not a new page.
- The first `answer` wins; a later `answer` is `already_answered`.

### Pushes per transition

In milestone 2, FCM is the only channel to the sender; the WebSocket arrives in milestone 4.

| Transition | Pushes |
| --- | --- |
| `delivered` | `page_state` `delivered` to the sender |
| `acknowledge` | `page_ack` to the other recipient devices; `page_state` `acknowledged` to the sender |
| `answer` | `page_answered` to the sender; `page_cancel` `answered_elsewhere` to the other recipient devices |
| sender cancel | `page_cancel` `cancelled` to the recipient devices |
| answerer End | `page_state` `ended` to the sender |
| no delivery in 30 s | re-push the `page` to the recipient devices; `page_state` `not_delivered` to the sender |
| missed | `page_cancel` `missed` to the recipient devices; `page_state` `missed` to the sender |
| all pushes failed | `page_state` `failed` to the sender |

## 9. FCM data messages

All FCM messages are **data** messages — every value is a string. This section **extends** the
spec's message list. Every message carries a `type` field equal to the message name, plus the
fields listed below. Field names never use FCM reserved keys (`from`, `message_type`,
`collapse_key`, `google.*`, `gcm.*`).

| Message | To | Priority | Fields |
| --- | --- | --- | --- |
| `page` | recipient devices | high | `page_id`, `level`, `from_user`, `envelope` (JSON of the signed object) |
| `page_cancel` | recipient devices | high | `page_id`, `reason`: `cancelled` \| `answered_elsewhere` \| `missed` |
| `page_ack` | recipient devices **except** the acknowledging one | high | `page_id` (stop ringing, keep the notification) |
| `page_answered` | sender device | high | `page_id` (shows a notification) |
| `page_state` | sender device | normal | `page_id`, `state`: `delivered` \| `acknowledged` \| `not_delivered` \| `missed` \| `failed` \| `ended` |
| `roster` | all non-revoked devices | normal | `version` |
| `test` | one device (`pttd admin test-push`) | high | — (a "Test push" notification) |
| `check_in` | all non-revoked devices (milestone 6) | normal | — |

- **Every high-priority message must lead to a visible notification change.**
- **`page_cancel` still shows something:** the phone replaces the page notification with a short
  auto-dismissing one — "Page cancelled" (`cancelled`), "Answered on another phone"
  (`answered_elsewhere`) — or, for `missed`, keeps the persistent "Missed page from <name>"
  notification.
- FCM data payloads are limited to 4096 bytes. The server returns `invalid_request` for a page
  whose push would exceed the limit (a `page` is ~1 KB for 2 devices).
- `failed` = every push for the page failed permanently; the page then ends.
- A token FCM reports as unregistered is cleared from the device.
- **FCM time-to-live:** a `page` push is 15 min when `level` is `normal`, 24 h when `urgent`;
  every other message is 15 min, except `roster`, which is 24 h.
- **`delivered` before alerting:** the receiver posts `POST /v1/pages/{id}/delivered` *before*
  it starts alerting and silently drops the page if that returns `410 page_ended` (a stale or
  replayed push). If `delivered` fails for network reasons, it alerts anyway and retries the
  post via its outbox.

## 10. Admin CLI

Run over SSH, inside the container. These commands open the database directly (not the REST
API):

```
pttd admin bootstrap <name>            # refuses if an admin user already exists; prints the QR text and the QR
pttd admin bootstrap --reset <name>    # revokes every device, deletes the roster, creates a NEW admin user <name>, then prints its QR like bootstrap
pttd admin devices                     # list devices and users
pttd admin revoke <device id>          # revoke one device
pttd admin test-push <device id>       # send the `test` FCM message to one device
pttd admin status                      # page/roster/token counters
```
