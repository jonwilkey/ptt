# Wire protocol — milestones 2 and 4 (enrollment, paging and live talk)

This is the wire-format contract shared by the Go server (`pttd`) and the Android app for
milestone 2 (enrollment and paging) and milestone 4 (live talk). It covers the REST API, the page
state machine, the FCM data messages (§1-§10), and the WebSocket control protocol and the
end-to-end-encrypted audio frames of live talk (§11-§12). Where this document lists more than
[`spec.md`](spec.md) (for example the FCM message list in §9), it **extends** the spec; the spec
remains authoritative for everything this document does not cover.

**Scope.** This document covers enrollment, paging and live talk. Milestone-5 items (clip
fallback: `heard`, `listener_gap`, `clip`, `resume`, `resume_from`, the server's transmission
buffer, and clip frames) are named in §11.12 and §12.1 as **reserved, milestone 5** and not
otherwise specified. The in-app-update endpoints
(`GET /v1/app/latest`, `GET /v1/app/apk/<version>`) are defined in the spec but omitted here.
Test devices and two pre-provisioned test accounts are server-side details; they never appear in
`GET /v1/contacts` or in the family roster, and this document does not give them a wire form.

## Privacy

No log line, metric label, or `audit_log` row records a page id, session id, transmission id,
sender, recipient, or device id of a WebSocket participant. The audit log covers enrollment,
revocation, roster changes, and authentication failures only (WebSocket `hello` failures
included, §11.3). WebSocket metrics are unlabelled counters and gauges, except that closes may be
counted per close code (a closed set, §11.1) — never per device, page, or session.

## 1. Encodings

| Item | Encoding |
| --- | --- |
| Binary in JSON (keys, signatures, tokens, codes, secrets) | base64url **without** padding (RFC 4648 §5); called **b64u** |
| Timestamps | integer unix **milliseconds**, UTC |
| IDs (user, device, page, session, transmission) | lowercase canonical UUID, 36 characters (a transmission id is 16 raw bytes in the binary audio header, §12.1) |
| Character set | UTF-8 |

`user_id` is assigned by the server; `device_id`, `page_id`, and `session_id` are generated by
the phone; a `transmission_id` is generated by the **talking phone** (a random version-4 UUID from
a CSPRNG, one per floor request, §11.6, §12.4) and echoed by the server.

Decoders are strict: b64u values are rejected if padded or in the standard alphabet (Go
`base64.RawURLEncoding.Strict()`), and an ID that is not a canonical lowercase UUID is
`invalid_request` — the HPKE `info` input and the enrollment MAC both rely on fixed-length IDs.

### Errors

Every error is an HTTP status plus a JSON body of exactly one field:

```json
{"error": "<code>"}
```

| Code | Status | Meaning |
| --- | --- | --- |
| `invalid_request` | 400 | Body malformed or a field invalid |
| `unauthorized` | 401 | Missing/unknown device token, or no auth where a token is required |
| `forbidden` | 403 | Authenticated but not allowed (e.g. a non-admin on an admin endpoint) |
| `not_found` | 404 | No such resource |
| `method_not_allowed` | 405 | Right resource, wrong method |
| `conflict` | 409 | State conflict (see endpoints) |
| `code_invalid` | 400 | Enrollment code unknown, already used, or expired — **one code for all three** |
| `roster_invalid` | 400 | Roster signature, format, or content rejected |
| `roster_stale` | 409 | Roster version is not higher than the current one |
| `already_answered` | 409 | `answer` on a page another device already answered |
| `page_ended` | 410 | Any action on a page that has ended (except `cancel` → `204`), or `delivered` on a page another device answered |
| `rate_limited` | 429 | Too many requests; `Retry-After` header in seconds |

`code_invalid` deliberately gives no oracle: the server does not distinguish unknown, used, and
expired codes.

### Rate limits

| Endpoint | Limit |
| --- | --- |
| `POST /v1/enroll` | 5 / hour, per client IP |
| `POST /v1/pages` | 30 / minute, per device |

## 2. Secrets and keys

| Item | Generation | Where it lives |
| --- | --- | --- |
| Device token | 32 random bytes | App only; server stores **SHA-256** |
| Enrollment code | 16 random bytes | App QR + server (server stores **SHA-256**) |
| Enrollment secret | 32 random bytes | **Admin phone + QR only** — never sent to the server |
| Ed25519 signing key | per device | Phone (secret); public key in the roster |
| X25519 HPKE key | per device | Phone (secret); public key in the roster |

- **Device token.** Sent as `Authorization: Bearer <token>`, where `<token>` is the token b64u
  (43 characters). The server stores only `SHA-256(token)`; a leaked database does not yield a
  usable token.
- **Enrollment code.** The QR carries it b64u (22 characters). The `code_id` in a URL is
  `b64u(SHA-256(code bytes))` — a public, non-secret handle.
- **Enrollment secret.** Generated by the admin phone, present only in the QR. It is the key for
  the enrollment MAC in §5.
- **Device keys.** A fresh Ed25519 and a fresh X25519 key pair per device. Public keys are the
  raw 32-byte keys, b64u (43 characters). Signatures are raw RFC 8032 (64 bytes, b64u = 86
  characters). Both Tink keysets use the **RAW** output prefix: `ED25519_RAW` for signing (the
  default `ED25519` template prefixes signatures with 5 bytes) and
  `DHKEM_X25519_HKDF_SHA256_HKDF_SHA256_CHACHA20_POLY1305_RAW` for HPKE. An HPKE-wrapped key is
  exactly `enc(32) || ct(32+16)` = 80 bytes.

## 3. Signed objects

The roster and the page envelope travel as a **signed object** — a JSON envelope whose `payload`
is opaque bytes and whose `sig` is computed over those bytes:

```json
{
  "payload": "<b64u(payload bytes)>",
  "signer": "<device id>",
  "sig": "<b64u(signature)>"
}
```

- `payload` — the exact UTF-8 JSON serialization of the payload object. `sig` is computed over
  these **exact bytes**; there is no canonical-JSON step.
- `sig` = `Ed25519_sign(signer's secret key, ctx || 0x00 || payload bytes)`, where `ctx` is the
  ASCII context string and `0x00` is a single separator byte.
- A payload's JSON must use exactly the documented field names, case-sensitively, with no
  duplicate keys, no `null` values and every required field present. Every parser of a payload
  (server or phone) rejects anything else, as it does invalid UTF-8 (a lenient parser could otherwise read a different value than
  the strict one the other side uses).
- A verifier checks the signature over the received bytes **before** parsing `payload`. Parsing a
  tampered or malformed `payload` is a `roster_invalid` (roster) or a dropped message (envelope),
  not a parse crash.

Context strings:

| Context string | Used for |
| --- | --- |
| `ptt-roster-v1` | Family roster (signer: an admin device) |
| `ptt-envelope-v1` | Page envelope (signer: the sender device) |

## 4. Family roster

Payload object (the JSON that is b64u'd into a signed object's `payload`), signed with context
`ptt-roster-v1`:

```json
{
  "format": 1,
  "version": 7,
  "issued_at": 1789920000000,
  "devices": [
    {
      "id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
      "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
      "display_name": "Alex",
      "device_name": "Alex's phone",
      "admin": true,
      "ed25519": "<43 chars>",
      "x25519": "<43 chars>"
    }
  ]
}
```

- `format` — currently `1`; bump only for a payload-shape change.
- `version` — monotonic; a phone accepts a roster only if it is higher than the one it holds.
- `devices` — sorted by `id`; `id` is unique within a roster. At least one entry must have
  `admin: true`: a roster with no admin is rejected (by the server with `roster_invalid`, and by
  a phone), since nobody could ever sign the next one.
- `display_name` and `device_name` are 1 to 64 characters of valid UTF-8 with no control
  characters and some non-space content.
- `display_name` — the **person**; `device_name` — the **phone**. `admin` mirrors the user's
  `is_admin`.

**A phone accepts a roster only if** (in order):

1. the signature verifies under `ptt-roster-v1`;
2. the payload parses under §3's strict rules and is well-formed per §4 (format 1, devices sorted
   and unique, valid names and keys, at least one `admin`);
3. the `signer` is an **admin** device in the phone's *current* roster — at enrollment, one of the
   QR's admin keys; for the bootstrap phone, its own key;
4. `version` is higher than the current one.

**The server accepts `PUT /v1/roster` only if**:

- the signature verifies under `ptt-roster-v1`;
- the payload is well-formed (§3, §4);
- the `signer` is a non-revoked admin device in the server's current roster. If no roster exists
  yet, the signer's user is an admin **and** the roster lists the signer as an admin;
- `version` is higher than the current one (else `roster_stale`);
- every listed device exists on the server, is not revoked, and its `user_id`, Ed25519 key,
  X25519 key, and `admin` flag (= the user's `is_admin`) all match the server's records.

A device enrolled via a code but not yet listed in a roster is allowed (pending approval).
Omitting a device from a roster does **not** revoke it — revocation is the explicit
`POST /v1/devices/{id}/revoke`.

## 5. Enrollment

The QR encodes, as `pttenroll1:` followed by b64u(JSON):

```json
{
  "url": "https://ptt.example.com",
  "code": "<22 chars>",
  "secret": "<43 chars>",
  "admins": [
    { "id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57", "ed25519": "<43 chars>" }
  ]
}
```

Bootstrap QRs (`pttd admin bootstrap`) omit `secret` and `admins`.

**MAC** (admin enrollments only):

```
MAC = HMAC-SHA256(
        secret,
        "ptt-enroll-mac-v1" || 0x00 || code(16 bytes)
          || device_id(36 ASCII) || ed25519_pub(32) || x25519_pub(32)
      )
```

`code` is the raw 16 code bytes; `device_id` is the 36 ASCII characters of the UUID; the two
public keys are the raw 32-byte keys. The MAC is 32 bytes (b64u = 43 characters). Bootstrap
enrollments send no MAC.

**Flow:**

1. Admin phone `POST /v1/enrollment-codes` — gets a `code`, `code_id`, `expires_at`.
2. Admin phone shows the QR (URL + code + secret + the admin device ids/keys).
3. New phone generates its key pair and `device_id`, `POST /v1/enroll`s, and stores the returned
   device token.
4. Admin phone polls `GET /v1/enrollment-codes/{code_id}` every 2 s until `used`, verifies the
   returned `mac` against the MAC it computes with its own secret, and also checks the
   response's `admin` (== the `make_admin` it requested), `display_name` (== the name it
   requested), and `user_id` (== the `user_id` it requested, or, for a new person, a user id
   not already in its current roster) — otherwise it refuses to sign (this stops a malicious
   server attaching a phone to the wrong person or making it an admin). It then signs roster
   `version+1` that includes the new device (context `ptt-roster-v1`) and `PUT /v1/roster`.
5. Server sends an FCM `roster` message to all non-revoked devices (see §9).
6. New phone `GET /v1/roster` and verifies it: the signer must be one of the QR's admin keys, the
   roster must list that admin with the same key, and it must list the new phone itself with its
   own keys. Only then is the phone usable.

Enrolling (including re-enrolling after `pttd admin bootstrap --reset`) discards any earlier
local roster, so the version check starts over from the first roster accepted this way.

**Bootstrap phone:** after enrolling, it signs roster **version 1** containing only itself and
`PUT /v1/roster`s it — becoming the first admin.

## 6. REST endpoints

All bodies and responses are JSON. Authentication is `Authorization: Bearer <token>` (device
token) except `POST /v1/enroll` and `GET /healthz`, which are unauthenticated. Admin endpoints
require the caller's **user** to be an admin.

| Endpoint | Auth |
| --- | --- |
| `POST /v1/enrollment-codes` | admin |
| `GET /v1/enrollment-codes/{code_id}` | admin |
| `POST /v1/enroll` | none (rate-limited) |
| `PUT /v1/devices/me` | device |
| `POST /v1/devices/{id}/revoke` | admin |
| `GET /v1/contacts` | device |
| `GET /v1/roster` | device |
| `PUT /v1/roster` | admin |
| `POST /v1/pages` | device (rate-limited) |
| `POST /v1/pages/{id}/delivered` | device in envelope |
| `POST /v1/pages/{id}/acknowledge` | device in envelope |
| `POST /v1/pages/{id}/answer` | device in envelope |
| `POST /v1/pages/{id}/cancel` | sender (and answering device after an answer) |
| `GET /healthz` | none |

### `POST /v1/enrollment-codes` (admin)

```json
{ "display_name": "Alex", "make_admin": false, "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845" }
```

`user_id` adds the new device to an existing person; omit it to create a new person at enroll.
`display_name` is required unless `user_id` is given. With `user_id`, the code inherits that
user's `display_name` and `is_admin`; a `make_admin` that differs → `400 invalid_request` (omitted = inherit).
→ `201`

```json
{ "code": "<22 chars>", "code_id": "<22 chars>", "expires_at": 1789920000000 }
```

Codes expire after 24 hours.

### `GET /v1/enrollment-codes/{code_id}` (admin)

→ `200`

```json
{
  "status": "used",
  "device": {
    "id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
    "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
    "display_name": "Alex",
    "device_name": "Alex's phone",
    "admin": false,
    "ed25519": "<43 chars>",
    "x25519": "<43 chars>",
    "mac": "<43 chars>"
  }
}
```

`status` is `pending` | `used` | `expired`; `device` is present only when `used`. Once the
nightly cleanup has deleted the code → `404 not_found`.

### `POST /v1/enroll` (none)

```json
{
  "code": "<22 chars>",
  "device_id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
  "device_name": "Alex's phone",
  "ed25519": "<43 chars>",
  "x25519": "<43 chars>",
  "mac": "<43 chars>",
  "fcm_token": "<FCM token>",
  "app_version": "0.2.0"
}
```

`mac` is required for codes created by an admin phone and must be absent for bootstrap codes
(otherwise `400 invalid_request`). An existing `device_id` → `409 conflict`. The body is fully
validated before the code is consumed, and the code is consumed atomically with creating the
device.

→ `201`

```json
{
  "token": "<43 chars>",
  "device_id": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
  "user_id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
  "display_name": "Alex",
  "admin": false
}
```

### `PUT /v1/devices/me` (device)

```json
{
  "fcm_token": "<FCM token>",
  "app_version": "0.2.0",
  "device_name": "Alex's phone",
  "checklist": { "battery_ok": false }
}
```

All fields optional; absent fields are unchanged. A `false` checklist item drives the `warning`
presence in `GET /v1/contacts`. → `204`.

### `POST /v1/devices/{id}/revoke` (admin)

→ `204`, idempotent. The phone flow for removing a device is: sign and `PUT` a roster without the
device, **then** revoke it. Revoking also closes the device's WebSocket (§11.9).

### `GET /v1/contacts` (device)

→ `200`

```json
{
  "users": [
    { "id": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845", "display_name": "Alex", "admin": true, "presence": "ok" }
  ]
}
```

Only users with at least one non-revoked, non-test device are listed (so people orphaned by
`bootstrap --reset` disappear until they re-enroll). `presence` is `ok` | `warning` | `offline`. A user is `offline` if none of their non-revoked
devices has been seen in 48 h; otherwise `warning` if any device's latest checklist has a `false`
item; otherwise `ok`.

### `GET /v1/roster` (device)

→ `200` the signed object (§3) from §4, or `404 not_found` if none exists.

### `PUT /v1/roster` (admin)

Body is the signed object (§3) from §4. → `204` on success; `400 roster_invalid` / `409
roster_stale` otherwise.

### `POST /v1/pages` (device)

```json
{
  "id": "5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13",
  "to": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
  "level": "urgent",
  "session_id": "a8d4e6b2-71c9-4f30-8b5e-2c9a1d7e3f60",
  "envelope": { "payload": "<b64u>", "signer": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57", "sig": "<b64u>" }
}
```

`envelope` is a signed object (§3) whose payload is the page envelope (§7). → `201`

```json
{ "id": "5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13", "state": "ringing" }
```

- Same `id` + same body → `200` with the current state (idempotent retry).
  “Same body” means `to`, `level`, and `session_id` are equal, and the decoded envelope fields
  `payload`, `signer`, and `sig` are byte-equal. Idempotent retries do not count against the
  client's rate limit.
- Same `id` after the page has ended → `200` with `{"id":"5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13","state":"ended"}`; the server
  **never re-pushes** it.
- Same `id` with a different body → `409 conflict`.
- If none of the devices in `keys` is non-revoked, the page fails at once → `201
  {"id","state":"ended"}` and it is tombstoned; no `page_state` push is sent.
- Paging your own user is allowed (Test alert).

### `POST /v1/pages/{id}/delivered`

Only a device listed in the envelope's `keys` may call it (any other caller → `403 forbidden`).
→ `200`

```json
{ "state": "ringing" }
```

`state` is `ringing`, `acknowledged` or `answered`; repeats return the current state again.
`answered` is returned only to the device that answered. If another device answered, or the page
has ended, → `410 page_ended`. Unknown `id` with no tombstone → `404 not_found`. The first call
sets the delivered flag. The phone's use of the state is in §9.

### `POST /v1/pages/{id}/acknowledge` · `/answer`

Only a device listed in the envelope's `keys` may call these; any other caller → `403
forbidden`. Repeats are idempotent (`204`). `answer` after another
device has answered → `409 already_answered`. Unknown `id` with no tombstone → `404
not_found`; a tombstoned page → `410 page_ended` (except `cancel`, below). For **every** page
action the client's outbox treats `2xx`, `410 page_ended`, and `409 already_answered` as final
and deletes the row.

### `POST /v1/pages/{id}/cancel`

The sender may call it any time; after an answer, the answering device may too (this is the
"End" on the answer screen). Any other caller → `403 forbidden`; unknown `id` with no tombstone
→ `404 not_found`. → `204`, idempotent — including on a **tombstoned** page (it is already over,
and `cancel` is final). While the page has a live session (§11.5), a WebSocket `session_end`
from a participant has the same effect as this call; both paths end the page the same way.

### `GET /healthz`

Unchanged from the spec (liveness probe).

## 7. Page envelope

Payload object signed with context `ptt-envelope-v1` by the **sender** device:

```json
{
  "format": 1,
  "page_id": "5f0c2a9e-3b1d-4c7a-9e21-6d8b0f4a7c13",
  "session_id": "a8d4e6b2-71c9-4f30-8b5e-2c9a1d7e3f60",
  "from_device": "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57",
  "to_user": "0b7e4c1d-9a2f-4e68-b3c5-71d0a9e2f845",
  "level": "normal",
  "created_at": 1789920000000,
  "keys": {
    "c3e9a7f1-5d2b-4b84-a6e0-9f1c8d3b2a57": "<b64u(HPKE enc || ciphertext)>"
  }
}
```

- `keys` maps each **recipient device id** to the HPKE-encryption of a 32-byte **session key**
  for that device. The sender wraps the key for exactly the devices in its current verified
  roster (§4) whose `user_id` is `to` — never from the server's contacts list.
- **HPKE** (RFC 9180) base mode: `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`,
  `ChaCha20-Poly1305`. Plaintext is the 32-byte session key. `info` =
  `"ptt-session-key-v1" || 0x00 || page_id || session_id || recipient device_id` (all ASCII).
  AAD is empty — Tink `HybridEncrypt` `contextInfo` = `info`. The keyset uses the
  `DHKEM_X25519_HKDF_SHA256_HKDF_SHA256_CHACHA20_POLY1305_RAW` template (RAW output prefix),
  so a wrapped key is exactly `enc(32) || ct(32+16)` = 80 bytes (b64u = 108 characters).

**Server** (never decrypts): parses the payload (not the signature) and rejects with
`invalid_request` unless the envelope's `signer` and the payload's `from_device` both equal the
caller's device id, `page_id`, `session_id`, `to_user`, and `level` equal the request's `id`,
`session_id`, `to`, and `level`, `keys` is non-empty, and every device id in `keys` is a device
of `to`. The sender and every device in `keys` must agree on whether they are test devices (a
page never crosses the test/real boundary). Entries for revoked devices are ignored, not pushed; the server pushes to the
non-revoked devices in `keys`, and if none remain the page ends as `failed`.

**Receivers:** verify the signature with `from_device`'s Ed25519 key from their own verified
roster, then check that `page_id` and `level` equal the push fields, that `to_user` is their
own user, that their own device id is in `keys`, that `from_device` is in the roster, and that
`from_user` equals that roster entry's `user_id` — dropping the message on signature failure or
any failed check. HPKE-decrypt their `keys` entry for the session key. The caller name shown
to the user comes from the roster entry, never from the server.

## 8. Page states and timers

Server-side states:

```
ringing ──▶ acknowledged (optional) ──▶ answered
```

A page is then **deleted** ("ended") on cancel, on missed, on failed, or on answered-page expiry.
`delivered_at` is a **flag**, not a state.

| Timer | Value |
| --- | --- |
| No `delivered` within | 30 s → re-push and tell the sender `not_delivered`; re-push again at 2 min |
| Normal page unanswered (acked or not) | 15 min → **missed** |
| Urgent page | **never** times out |
| Answered page, not yet joined by both devices (§11.5) | session ends `idle` **15 min** after the answer (the milestone-2 expiry, kept as the cap) |
| Answered page, both devices have joined | session ends `idle` after **2 min** with no floor activity (§11.5) |

- Ended pages leave a **tombstone** (id only) for **24 h**, so a late idempotent `POST /v1/pages`
  returns `ended`, not a new page.
- The first `answer` wins; a later `answer` is `already_answered`.

### Pushes per transition

Progress reaches a participant over the **WebSocket** when its socket is *live*, and by FCM
otherwise. A participant's socket is **live** when it is joined to the page's session and has sent
any message in the last 15 s. For the normal-priority `page_state` pushes the server picks **one
channel** at the instant of the transition: a live socket gets the WebSocket message and the FCM
push is **skipped**; otherwise the FCM push is sent as before. A phone that joins later learns the
current state from the join snapshot (§11.4), so a transition sent to a dead socket is not lost.

**`page_answered` is the exception: it always goes by FCM to the sender, and also over the
WebSocket (`page_state` `answered`) when the sender's socket is live.** It is high priority and
the only thing that reopens the talk screen of a sender whose process died: the "live" window
(up to 15 s of silence) cannot prove the process is alive, and a skipped push would leave the
sender at "Delivered" forever. The app de-duplicates by `page_id`: if it is already in that
session it only updates its ongoing notification (so the high-priority message still ends in a
visible notification change, §9).

| Transition | WebSocket, to each live participant | FCM, to the sender | FCM, to the recipient devices |
| --- | --- | --- | --- |
| `delivered` | sender: `page_state` `delivered`, if the page is still `ringing` | same, only if the sender is not live | — |
| `acknowledge` | sender: `page_state` `acknowledged` | same, only if not live | `page_ack` to the other recipient devices |
| `answer` | sender: `page_state` `answered` | `page_answered`, **always** | `page_cancel` `answered_elsewhere` to the other recipient devices |
| sender cancel | sender: `session_end` `ended_by_you`; answering device: `session_end` `ended_by_peer` | — | before an answer: `page_cancel` `cancelled` to the recipient devices; after an answer: to the answering device only, and only if it is not live |
| answerer End (REST `cancel` or WebSocket `session_end`) | answerer: `session_end` `ended_by_you`; sender: `session_end` `ended_by_peer` | `page_state` `ended`, only if the sender is not live | — |
| session idle (§11.5) | each participant: `session_end` `idle` | `page_state` `ended`, only if the sender is not live | — |
| no delivery in 30 s | sender: `page_state` `not_delivered` | same, only if not live | re-push the `page` (if the server was down past both deadlines, one re-push covers both) |
| missed | sender: `session_end` `missed` | `page_state` `missed`, only if not live | `page_cancel` `missed` |
| all pushes failed | sender: `session_end` `failed` | `page_state` `failed`, only if not live | — |

Over the WebSocket the **non-terminal** page states are `page_state` messages (`ringing`,
`delivered`, `acknowledged`, `not_delivered`, `answered`) and every **terminal** outcome
(`ended`, `missed`, `failed`, cancel, idle) is a `session_end` with a reason (§11.5). FCM keeps the
§9 `page_state` values (`delivered` | `acknowledged` | `not_delivered` | `missed` | `failed` |
`ended`) and `page_answered`. A cancel by the sender is never pushed back to the sender over FCM.

## 9. FCM data messages

All FCM messages are **data** messages — every value is a string. This section **extends** the
spec's message list. Every message carries a `type` field equal to the message name, plus the
fields listed below. Field names never use FCM reserved keys (`from`, `message_type`,
`collapse_key`, `google.*`, `gcm.*`).

| Message | To | Priority | Fields |
| --- | --- | --- | --- |
| `page` | recipient devices | high | `page_id`, `level`, `from_user`, `envelope` (JSON of the signed object) |
| `page_cancel` | recipient devices | high | `page_id`, `reason`: `cancelled` \| `answered_elsewhere` \| `missed` |
| `page_ack` | recipient devices **except** the acknowledging one | high | `page_id` (stop ringing, keep the notification) |
| `page_answered` | sender device | high | `page_id` (shows a notification) |
| `page_state` | sender device | normal | `page_id`, `state`: `delivered` \| `acknowledged` \| `not_delivered` \| `missed` \| `failed` \| `ended` |
| `roster` | all non-revoked devices | normal | `version` |
| `test` | one device (`pttd admin test-push`) | high | — (a "Test push" notification) |
| `check_in` | all non-revoked devices (milestone 6) | normal | — |

- **Every high-priority message must lead to a visible notification change.**
- **`page_cancel` still shows something:** the phone replaces the page notification with a short
  auto-dismissing one — "Page cancelled" (`cancelled`), "Answered on another phone"
  (`answered_elsewhere`) — or, for `missed`, keeps the persistent "Missed page from <name>"
  notification.
- FCM data payloads are limited to 4096 bytes. The server returns `invalid_request` for a page
  whose push would exceed the limit (a `page` is ~1 KB for 2 devices).
- `failed` = every push for the page failed permanently; the page then ends.
- A token FCM reports as unregistered is cleared from the device.
- **FCM time-to-live:** a `page` push is 15 min when `level` is `normal`, 24 h when `urgent`;
  every other message is 15 min, except `roster`, which is 24 h.
- **`delivered` before alerting:** the receiver posts `POST /v1/pages/{id}/delivered` *before*
  it starts alerting, and acts on the returned `state`: `ringing` → alert as usual;
  `acknowledged` → another device already acknowledged, so post the notification silently (the
  page is still answerable); `answered` (this device answered it) → show the answered page, do
  not ring. `410 page_ended` (the page ended or another device answered; also a stale or
  replayed push) → drop the page silently. If `delivered` fails for network reasons, it alerts
  anyway and retries the post via its outbox.

## 11. WebSocket protocol (`GET /v1/ws`)

Live talk runs over one WebSocket per phone, opened by `TalkService` only while a page or
session is active. The upgrade is on the same TLS origin as the REST API (`wss://`).

### 11.1 Connection, framing, versioning, close codes

- **No credentials in the upgrade.** The URL has no query and the server ignores `Authorization`:
  the token goes in the first frame (§11.3), so it never reaches a proxy or access log.
- **Compression is off** (no `permessage-deflate`); the audio is incompressible ciphertext.
- **Text frames** are JSON control messages (§11.2). **Binary frames** are audio (§12).
- **Size limits:** a text frame is at most **1024** bytes, a binary frame at most **1312**
  bytes (`MaxFrameSize`, §12.1). Larger → close `4413`.
- **The server is strict about client messages**, exactly like a signed payload (§3): UTF-8, one
  object, no duplicate keys, case-sensitive keys, no `null`, exactly the keys listed for the
  message (none missing, none extra), IDs as canonical lowercase UUIDs (§1). Every message has a
  string `type`. "`type` first" in the tables is a rule for **emitters** only: a parser MUST NOT
  depend on key order. An unknown `type`, or a message that is wrong for the connection's state
  (§11.3, §11.4), closes the socket with `4400`.
- **Clients are lenient about server messages** (see Versioning): they MUST ignore a server →
  client message whose `type` they do not know.
- **One socket per device.** When a device completes `hello` while it already has an open
  socket, the server closes the **old** socket with `4409` and the new one proceeds. The new
  socket starts with no session; the old socket's participation ends (the peer sees `peer_left`)
  and the device must `join` again. A client that gets `4409` must not reconnect on its own.

**Versioning.** `hello` carries an integer `protocol` in both directions; **`1` is the protocol of
this document (milestone 4)**. The client sends the highest it speaks; the server replies with
`min(client's, its own highest)`, and from then on:

- the server never sends a message `type`, field, or enum value (a `state`, `reason` or `code`)
  defined only by a higher protocol than the one it replied with;
- a client that sent a higher `protocol` than the server's reply falls back to the server's, and
  sends only what that protocol defines (the server stays strict on client messages);
- clients MUST ignore unknown server → client `type`s and unknown fields in server messages, treat an unknown `session_end.reason` as a
  generic end of the session (the same as `ended_by_peer`), an unknown `floor_released.reason` as
  `released`, an unknown `error.code` as non-fatal, and an unknown `page_state.state` as no change.

Milestone 5 therefore ships as `protocol` 2: its new types (§11.12) are sent only to clients that
announced 2. **Rollback and the 30-day rule:** a server rolled back to the previous release answers
a newer app with its lower `protocol` and the app falls back; and for 30 days after any protocol
bump the new server must still serve the previous protocol and the new app must still speak it, so
that a rollback of either side (or a phone that has not updated yet) keeps working. Remove support
for a protocol only after that window.

**Close codes.** The server closes with a code and a short fixed reason token (the name in the
table), never with text derived from client input. After a `session_end` (§11.5) it closes with
`1000`.

| Code | Name | Meaning | Client reaction |
| --- | --- | --- | --- |
| `1000` | `normal` | Normal closure (after `session_end`, or a client closing) | — |
| `4400` | `protocol_error` | Malformed JSON or shape (including a malformed `hello`), unknown or out-of-state message, malformed binary frame (§12.1) | Fix the bug; reconnect with backoff only if the session is still active |
| `4401` | `unauthorized` | `hello` token not a valid 43-character b64u, or unknown, or revoked (one code for all three) | Stop; treat like REST `401` |
| `4403` | `revoked` | The device was revoked while connected (§11.9) | Stop; treat like REST `401` |
| `4408` | `timeout` | No `hello` within 10 s, no successful `join` within 30 s of `hello`, no message at all for 30 s, or a peer not reading its socket (§11.7) | Reconnect with backoff if the session is still active |
| `4409` | `replaced` | Another socket from this device took over | Do not reconnect automatically |
| `4413` | `too_large` | A frame over the size limit | As `4400` |
| `4429` | `rate_limited` | Message-rate limit exceeded (§11.10) | Reconnect with backoff |
| `4500` | `server_error` | Unexpected server error | Reconnect with backoff |
| `4503` | `server_restarting` | Server shutting down | Reconnect with backoff, then `join` again (§11.5) |

### 11.2 Messages

IDs are canonical UUIDs; `t` and `server_time` are integers in unix milliseconds (`t` is the
client's clock and is 0 to 2^53−1); `protocol` is an integer of at least 1.

**Client → server**

| `type` | Other fields | Meaning |
| --- | --- | --- |
| `hello` | `protocol`, `token` (b64u, 43 chars), `app_version` (string, as in `PUT /v1/devices/me`) | Authenticate (§11.3) |
| `join` | `session_id` | Join the session of a page (§11.4) |
| `floor_request` | `transmission_id` (a fresh random version-4 UUID) | Ask for the floor (§11.6) |
| `floor_release` | `transmission_id` | Give up the floor |
| `session_end` | — | End the session; same effect as REST `cancel` (§11.5) |
| `ping` | `t` | Liveness and RTT (§11.8) |

**Server → client**

| `type` | Other fields | Meaning |
| --- | --- | --- |
| `hello` | `protocol`, `device_id`, `server_time` | Authenticated (§11.3) |
| `page_state` | `page_id`, `state` | Page progress; `state` is `ringing` \| `delivered` \| `acknowledged` \| `not_delivered` \| `answered` (§11.4, §8) |
| `peer_joined` | `device_id` | The other participant joined |
| `peer_left` | `device_id` | The other participant's socket closed or was replaced |
| `floor_granted` | `talker` (device id), `transmission_id` | Sent to **both** participants; also in the join snapshot while the floor is held (§11.4) |
| `floor_busy` | — | Sent to the requester only |
| `floor_released` | `talker`, `transmission_id`, `reason` | Sent to the participants still connected (§11.6) |
| `session_end` | `reason` | The session is over (§11.5) |
| `error` | `code` | A well-formed request refused (§11.4, §11.6). Never closes the socket |
| `pong` | `t`, `server_time` | Answer to `ping` |

`error.code` is one of `not_found` (a `join` for a page that does not exist, has ended, or is not
yours to join — one code for all three), `no_peer` (`floor_request` while the other participant has
not joined, or on a self page, §11.4) or `bad_transmission_id` (`floor_request` with a
`transmission_id` that is not a canonical lowercase version-4 UUID, or one already used in this
session, §11.6).

**Reserved, milestone 5** (names and fields fixed now, sent only with `protocol` ≥ 2; a
`protocol` 1 server treats the client types as unknown, `4400`): `heard {transmission_id,
last_seq}` (client → server), `listener_gap {transmission_id}` (server → talker), `clip
{transmission_id}` (server → listener, announcing a replay as a clip), `resume {transmission_id}`
(client → server), `resume_from {last_seq}` (server → talker). See §11.12.

### 11.3 Authentication (`hello`)

1. The client sends `hello {protocol, token, app_version}` within **10 s** of the upgrade; the
   server closes with `4408` otherwise. Before `hello` the server accepts nothing else, at most 512
   bytes, and caps unauthenticated sockets at 64 (more upgrades → `503`). A binary frame before
   `hello` is `4400`.
2. **Not valid strict JSON, wrong keys or types, `protocol` not an integer ≥ 1, or an invalid
   `app_version` → close `4400`, no audit row.**
3. **`token` not a valid strict b64u of exactly 32 bytes (43 characters) → close `4401`, no audit
   row.**
4. **A well-formed token that is unknown, or whose device has `revoked_at` set → close `4401`
   (one code for both, no oracle) and one `auth_failure` audit row** with no actor, through the
   **same throttle** as REST authentication failures (`internal/httpapi/auth.go`: one row per
   window however many sockets fail). The row holds no token and no IP address.
5. On success the server replaces any older socket of the device (`4409`, §11.1), does whatever REST
   authentication does for `last_seen_at`, and replies `hello {protocol, device_id, server_time}`.
   The client uses `server_time` only to display clock skew; nothing is signed with it.

`app_version` is informational (stored as `PUT /v1/devices/me` would); the server never refuses a
`hello` for it. Version negotiation is `protocol` alone (§11.1).

### 11.4 Joining a session

`join {session_id}` follows `hello`. The server looks up the active page with that `session_id`
**and the caller's role** — `from_device` equals the caller (the sender), or `answered_by` equals
the caller (the answering device) — and accepts the join only for:

- the page's **sender**, at **any time while the page exists** (so it can wait for progress), and
- the page's **answering device** — the device recorded in `active_pages.answered_by` by `answer` —
  after the `answer`.

Every other case (no such page, the page ended, the caller is another recipient device or not a
participant, a recipient before `answer`) → `error {code: "not_found"}`. **A refused join does not
count:** the socket stays open and unjoined and may `join` again (to the same or another session)
until 30 s after `hello`, when an unjoined socket is closed `4408`. A client joins only **after** the
REST call that creates the session state has returned `2xx` (`POST /v1/pages` for the sender,
`POST /v1/pages/{id}/answer` for the answerer), so `not_found` after that means the page is over —
the client stops and closes. A second **successful** `join` on a socket is `4400`.

On success the server sends the joiner, in order:

1. `page_state {page_id, state}` — the snapshot, which doubles as the join acknowledgement:
   `answered` if answered, else `acknowledged` if acknowledged, else `delivered` if the delivered
   flag is set, else `not_delivered` if the flag is unset and at least 30 s have passed since
   `created_at`, else `ringing`.
2. `peer_joined {device_id}` — only if the other participant is already joined.
3. `floor_granted {talker, transmission_id}` — only if the floor is currently held (so a phone that
   rejoins in the middle of a transmission can keep decrypting it; the receiver's rule is in §12.4).

and sends the other participant `peer_joined {device_id}` (the joiner). The server processes a
socket's messages in order, so a client may send `floor_request` right behind `join`;
`floor_request`, `floor_release` and `session_end` on a socket that has **not** joined are `4400`,
and a binary frame on an unjoined socket is dropped silently (§11.7).

**Self page (Test alert).** When `from_device` equals `answered_by` the phone is both participants.
The server treats a `join` there as sender-only; there is no second participant, so no session in
the sense of §11.5 and no floor (`floor_request` → `error no_peer`). The app does not open the talk
screen for a self page, so in practice it never joins.

**Server changes for 14b.** The `answered_by` column already exists (migration `00003`), so the
answering device needs no schema change. `session_id` is only indexed, not unique: it must be
**unique among all active pages**. `POST /v1/pages` returns `409 conflict` when a *different* page
id, still active, already uses the `session_id` (a retry with the same page id is the idempotent
case of §6 and is not a conflict; a tombstoned page does not hold its `session_id`). This is
expand-only (for example a unique index on `active_pages (session_id)`).

### 11.5 Session lifecycle

A **session** exists from `answer` until it ends; it is purely in-memory state on top of the page
row (the joined sockets, the floor, the timers). Before `answer` the sender may already be joined
(waiting), but nobody can talk (`floor_request` → `no_peer`).

**What ends a session:**

| Trigger | `reason` to the participants' sockets |
| --- | --- |
| A participant sends `session_end` (WebSocket), or calls REST `cancel` (the sender any time, the answering device after `answer`) | `ended_by_you` to the initiator's own socket (if it has one joined), `ended_by_peer` to the other |
| **2 minutes** with no floor activity once **both** participants have joined | `idle` to both |
| The **15-minute** answered-page cap while both have not yet been joined at the same time | `idle` to whoever is joined |
| The unanswered page expires (normal, 15 min) | `missed` to the sender |
| Every push failed (§9) | `failed` to the sender |
| A participant is revoked (§11.9) | `ended_by_peer` to the other (the revoked socket gets `4403`, not `session_end`) |

The closed set of `session_end.reason` is **`ended_by_you`, `ended_by_peer`, `idle`, `missed`,
`failed`**. (A sender `cancel` before any answer needs no reason for a receiver — no recipient is
joined — and the recipients' devices are told by FCM `page_cancel`, §8.)

**The 2-minute idle timer** is armed when the second participant joins (both sockets joined at the
same time, for the first time) and is reset to 2 minutes by every `floor_granted` and every
`floor_released`. Pings, frames, and joins do not reset it. If a participant's socket drops
afterwards the timer keeps running; a rejoin within it keeps the session. **The 15-minute cap**
(the milestone-2 answered-page expiry, kept because it is the only bound while a participant never
shows up, for example a sender who swiped the app away and ignores `page_answered`) runs from the
`answer` and is cancelled the first time both participants are joined together. There is no
absolute maximum session length while the floor keeps changing hands.

**On end** the server, in this order: **commits** the deletion of the page row (leaving the 24 h
tombstone, §8), so a crash after this point cannot resurrect the session; then writes `session_end`
to each joined socket; discards all in-memory session state (floor, timers, send queues); and
closes the sockets with `1000`. The server therefore owns closing; a client that receives
`session_end` stops sending, discards its session key, and closes if the server has not.

**State is not persisted.** The page row (with `answered_by`) is the only durable part; after a
`pttd` restart the sockets are closed `4503`, and clients reconnect and `join` again — the join
rebuilds the session (the idle timer starts over, an in-progress transmission is lost, and the
server's record of used transmission ids is gone, which is why nonce safety does not rest on it,
§12.4). Session keys on the phones are not persisted either, but a phone can unwrap the same
session key again from its envelope (for example after its process died), so a phone's own state
cannot be assumed to survive either.

### 11.6 Floor control

The server owns the floor of a session; its decisions are serialized per session, so **the first
request processed wins**. The **talker mints the `transmission_id`** (§12.4).

- `floor_request {transmission_id}`: the id must be a canonical lowercase **version-4 UUID** that
  has not been used in this session (the server keeps the ids it has granted for the life of the
  session in memory); otherwise `error {code: "bad_transmission_id"}` and nothing else happens.
  Otherwise, if the floor is free and the peer is joined, the server sends `floor_granted {talker,
  transmission_id}` to **both** participants, `talker` being the requester's device id and
  `transmission_id` echoed unchanged. If the floor is held, the requester gets `floor_busy` (and
  nothing else); the id of a request answered `floor_busy` or `error` was never granted, but a
  client MUST still use a **new** id for its next request. A `floor_request` while the peer is not
  joined → `error no_peer`. A `floor_request` from the current talker is ignored. A revoked
  device's request is refused with close `4403` (§11.9).
- `floor_release {transmission_id}`: from the current talker with the current id, it frees the
  floor and the server sends `floor_released {talker, transmission_id, reason: "released"}` to
  **both**. A release from anyone else, or with another id (a stale message that crossed the
  server's own release) is **ignored silently**; it is not an error.
- The server also releases the floor by itself and sends `floor_released` to the participants still
  connected, with a `reason` from the closed set **`released`** (talker's `floor_release`),
  **`silence`** (1 s with no accepted frame since the last accepted frame; before the first frame
  the allowance is **3 s from the grant**, to cover the talker's round trip and encoder start),
  **`max_length`** (60 s after the grant), **`disconnected`** (the talker's socket closed or was
  replaced; sent to the peer only).
- Releasing the floor never ends the session.
- The server does **not** enforce the first-talker rule (the receiver speaks first); that is the
  sender app's concern (spec, "Sending a page").

**What a phone does with `floor_granted`** (the server may lie, §12.6):

- The **answering device** accepts a `talker` only if it is its own device id or the envelope's
  `from_device`. The **sender** accepts only its own id or the device id of the `peer_joined` that
  it received, which must be a device in its envelope's `keys`. Any other grant is ignored.
- It plays frames only when `talker` is the **peer**. It sends audio only under the rules of §12.4
  (the grant must answer its own outstanding `floor_request`).
- A `floor_granted` that names the phone itself **without an outstanding `floor_request` of its
  own** (a lying or replayed grant, or one surviving the phone's own restart) → the phone sends
  `floor_release` for that id and sends **no audio**.
- The receiver-side rule about repeated ids (including the rejoin snapshot) is §12.4 rule 4.

### 11.7 Frame relay and the send queue

Only the participant holding the floor may send audio. For each binary frame from a joined socket
the server runs `audioframe.Parse` (§12.1) — a frame that fails it closes the socket with `4400` —
and then:

- if the sender is the **current talker** and the header's `transmission_id` is the **current**
  one, it counts as activity for the silence timer (even if the peer has left) and is relayed
  **byte for byte** to the other participant if that participant is joined;
- otherwise (not the talker, a stale or unknown `transmission_id`, a socket that has not joined, a
  floor already released) the frame is **dropped silently**. No `error` is sent: late frames after
  a `silence` or `max_length` release are normal, and the talker learns of the release from
  `floor_released`.

The server does not look at `seq` beyond `Parse`'s bound: it does not order, deduplicate or
authenticate frames (it cannot — §12.6), so reordering, delay and replay by the server are possible
and are handled by the receiver (§12.5).

**One ordered outbound queue per socket** carries control messages and relayed frames alike, in the
order the server produced them, so `floor_granted` always precedes the frames of its
transmission and `floor_released` follows the last frame relayed for it. **The limit counts frames
only:** when **25 frames (500 ms)** are already queued the next frame is dropped (the
latency target is under 700 ms, so a longer queue would only deliver stale audio; milestone 5 turns
an overflow into `listener_gap`). **Control messages are never dropped.** A socket whose queue grows
past 256 entries in total (a peer that is not reading) is closed `4408`.

### 11.8 `ping` / `pong`, timeouts

The client sends `ping {t}` every **10 s** while connected (and may send one right after `hello`).
The server answers at once with `pong {t, server_time}`, echoing `t` unchanged; the client computes
RTT as `now − t` on its own clock. The server closes a socket `4408` that has sent no message at
all (text or binary) for **30 s**. WebSocket protocol-level ping/pong frames are not used by the app
and do not count as messages.

### 11.9 Revocation

- **Admin REST** `POST /v1/devices/{id}/revoke` closes that device's socket immediately with `4403`.
- **`pttd admin revoke`** runs in another process and only writes `revoked_at`, so it cannot reach
  the sockets. The server therefore **sweeps**: every **5 s** it checks `revoked_at` for all
  connected devices with one query and closes any revoked device's socket with `4403`; in addition
  a `hello`, a `join`, and every `floor_request` re-check `revoked_at` first. A revoked device can
  therefore not start a new transmission, and may finish one in progress for up to 5 s.
- Closing a participant's socket for revocation also ends its session: the other participant gets
  `session_end ended_by_peer` (§11.5). Whether M2's revoke already ends the revoked device's
  ringing pages is unchanged by this document.

### 11.10 Limits

| What | Limit | Over the limit |
| --- | --- | --- |
| Upgrades | 30 / minute per client IP | `429`, `Retry-After`, as §1 |
| Unauthenticated sockets | 64 at once | `503` on upgrade |
| Text messages | 20 / s sustained, burst 40, per socket | close `4429` |
| Binary frames | 100 / s sustained, burst 200 (a talker sends 50 / s), per socket | close `4429` |
| Text frame / binary frame size | 1024 / 1312 bytes | close `4413` |

### 11.11 Notes for the implementers

- The WebSocket and REST share the state machine: `session_end` and REST `cancel` call the same
  server function and are both idempotent; a client must treat a REST `410 page_ended` or `204`
  and a `session_end` as the same final fact.
- A phone has one page or session at a time (spec); a new session needs a new socket (the old one
  is closed by `1000` after `session_end`).

### 11.12 Reserved, milestone 5

`heard`, `listener_gap`, `clip`, `resume`, `resume_from`, binary frame type `0x02`, the server's
in-memory transmission buffer and the clip frames are **not specified** beyond their names and
fields in §11.2 and §12.1. To stay forward-compatible, milestone 4 already: keeps all state
per `transmission_id`; has the talker keep each sealed frame (never the plaintext) of the
current transmission in memory so a resend is a resend of bytes (§12.4); rejects unknown binary
types and client message types with `4400`; and negotiates `protocol` (§11.1), so milestone-5
messages reach only clients that announced `protocol` 2. `no_peer` is a milestone-4 behavior
(milestone 5 may grant the floor with the peer away and buffer instead). **Milestone 5 must
revisit the 100 frames/s binary limit of §11.10 or pace resends**: a resend of a stored
transmission competes with live frames on the same socket.

## 12. Audio frames and per-frame encryption

Audio travels as **binary WebSocket frames**, one 20 ms Opus packet each, encrypted end to end
between the two phones. The server relays them (§11.7) and **never holds a key**.

### 12.1 Frame layout

```
offset  size  field
0       1     type            0x01 = live audio; 0x02 reserved for milestone-5 clips; all others rejected
1       16    transmission_id raw UUID bytes (big-endian field order, as in the 36-character text form)
17      4     seq             uint32, big-endian; starts at 0, +1 per 20 ms frame
21      n+16  ciphertext || GCM tag    n = Opus packet length
```

- The **21-byte header** (offset 0-20) is the AES-GCM **associated data**.
- An Opus packet is **1 to 1275** bytes (RFC 6716); a 24 kbps, 20 ms packet is about 60. The
  ciphertext is as long as the packet, so a whole frame is **38 to 1312** bytes
  (`audioframe.MinFrameSize` .. `MaxFrameSize`). An empty packet is never sent.
- `seq` is at most **4095** (`audioframe.MaxSeq`): a transmission lasts at most 60 s, which is 3000
  frames; the bound limits a receiver's replay state.
- Type `0x02` is **reserved, milestone 5** (buffered clips) and is rejected like any unknown type;
  milestone 4 never sends it.
- The server's parser (`server/internal/audioframe`, fuzzed) accepts a frame only if its length is
  in range, its type is `0x01` and `seq ≤ 4095`; a receiver applies the same checks first (§12.5).

### 12.2 Transmission key

Each transmission has its own AES-256-GCM key:

```
transmission_key = HKDF-SHA256(
    IKM  = session key (32 bytes, from the page envelope, §7),
    salt = empty,
    info = "ptt-transmission-key-v1" || 0x00 || session_id || talker_device_id || transmission_id,
    L    = 32)
```

- `session_id`, `talker_device_id` and `transmission_id` are each the 36-character lowercase
  canonical UUID text (§1), ASCII, concatenated with no separator (fixed length, so unambiguous).
- The **salt is empty** (HKDF then uses a block of zeros): the input is already a uniformly random
  256-bit key, and all domain separation is in `info`.
- **`talker_device_id` is part of `info`**, so two talkers can never share a key even if they use
  the same `transmission_id`. The receiver derives with the talker named in `floor_granted`; a
  server that names the wrong talker, or lies about the id, only makes decryption fail.

### 12.3 Nonce

The 12-byte GCM nonce is **8 zero bytes ‖ `seq` (4 bytes, big-endian)**. It never travels: both
sides compute it from the header. It is unique because the key is unique per (session, talker,
transmission) and `seq` never repeats within a transmission (§12.4). The header, including `seq`
and `transmission_id`, is the AAD, so a header altered in transit fails the tag.

### 12.4 Nonce-reuse defence (normative)

AES-GCM is catastrophically broken if one (key, nonce) pair ever encrypts two different
plaintexts, so nonce safety must not depend on any state that can be lost or on the server.
**The talker therefore mints the `transmission_id`** (a server-chosen id could repeat after a
server restart, and a phone's own memory of used ids is lost if its process dies and re-unwraps the
session key from the envelope). These rules are normative; every implementation MUST follow them.

1. **Minting.** For **every** `floor_request` the talker generates a fresh `transmission_id`: a
   random version-4 UUID (122 random bits) from a CSPRNG (`SecureRandom`), never derived from a
   clock or counter, and never reused — not after `floor_busy`, not after an `error`, not on a
   retry. Two ids colliding by chance is negligible, so key and nonce uniqueness hold even if every
   piece of state on both phones and the server is lost. The talker SHOULD also remember its ids
   for the life of the session key and refuse a duplicate.
2. **Sending.** A talker MUST NOT send audio unless a `floor_granted` names its own device id as
   `talker` **and** carries the `transmission_id` of its outstanding `floor_request`; every frame
   carries that id. A grant naming it without a matching outstanding request is answered with
   `floor_release` and no audio (§11.6).
3. **A (`transmission_id`, `seq`) pair MUST be encrypted at most once.** The talker numbers frames
   from 0 with no gaps and never reuses a `seq`; it MUST NOT encrypt a different plaintext under a
   pair it has used. In milestone 4 a talker whose socket drops loses the floor (`disconnected`,
   §11.6) and must send a new `floor_request` with a **new** id; continuing a transmission
   (`resume`) is milestone 5, and a milestone-5 resend sends the **stored ciphertext frame**, never a
   fresh encryption.
4. **A receiver refuses a repeated `transmission_id`, with one exception.** It keeps the ids it has
   seen in this session. A `floor_granted` whose id it has already seen is **refused** (and its
   frames ignored) — **unless** it equals the *current, not yet released* transmission and names the
   *same talker*; that is the join snapshot of a rejoin (§11.4) or a repeated message, and the
   receiver keeps its existing set of accepted `seq`s for it. An id for which it has seen
   `floor_released` is refused forever, for every talker. A grant naming another talker for an id in
   use, or a grant while another transmission is current and not released, is refused. (This is
   defence in depth against a lying server; rule 1 is what protects the nonce.)

   **Suspension.** When the receiver's own socket closes, its current transmission becomes
   *suspended*, because a `floor_released` sent while it was away never arrives. After it rejoins,
   a `floor_granted` with the same talker and id **resumes** the transmission and keeps its
   accepted-`seq` set; any other `floor_granted` first treats the suspended transmission as
   released (its id is refused forever) and is then judged as a fresh grant. Frames for a suspended
   transmission are dropped. Without this a receiver would stay deaf for the rest of the session.
5. **A receiver MUST drop a frame whose `seq` it has already accepted for that transmission**
   (replay), and MUST record a `seq` as accepted only **after** its tag verified (§12.5), so a
   forged frame cannot use up a sequence number. Out-of-order frames are accepted once each. The
   accepted set is per transmission: the same `seq` under a new `transmission_id` is a fresh frame.
6. Session keys and the sets above are discarded when the session ends (or the process dies); a key
   is never used for a second session (each page has a fresh random key, §7).

### 12.5 Receiving a frame

A receiver holds the session key, the `session_id`, and, from an accepted `floor_granted`, the
current talker and `transmission_id`. For each binary frame, in this order, dropping the frame at
the first failure:

1. length 38 to 1312 (`bad_length`);
2. `type == 0x01` (`bad_type`);
3. `seq ≤ 4095` (`bad_seq`);
4. `transmission_id` equals the current one from `floor_granted` (`wrong_transmission`);
5. derive the key (§12.2) with the talker from `floor_granted`; AES-256-GCM open with the nonce of
   §12.3 and AAD = the 21-byte header; a tag failure → `decrypt_failed`;
6. if `seq` was already accepted → drop as a replay; else mark it accepted and hand the packet to the
   jitter buffer and decoder.

A frame is never played before step 5 succeeds, nor when the talker is the receiver itself. Dropped
frames are not reported to the server.

### 12.6 What the server can and cannot do

The server reads the **header** (type, transmission id, seq): it needs them to relay and to run
floor control (§11.6, §11.7), and it can observe who is talking and for how long. It never has a
session key or a transmission key and so can neither read nor forge audio. It can **drop, delay,
reorder, duplicate or replay** frames, and it can lie in `floor_granted`; the defences are the AAD
(header tampering fails the tag), the unique key (§12.2), the talker-minted ids (§12.4) and the
rules of §12.4-§12.5. Server code must not log or count header fields per transmission.

**Known limitation (accepted).** A receiver that restarts re-unwraps the session key from its
envelope and so has lost its set of seen transmission ids; a lying server could then replay an old
whole transmission to it and the old audio would play as if new. The server still cannot decrypt
or forge audio, and a family-sized deployment accepts this.

### 12.7 Key lifetime

The session key arrives wrapped in the envelope (§7) and stays in memory only (spec: no
persistence). There is no ratchet in v1 (spec): a stolen device key later decrypts that device's
captured past sessions. This is accepted by the spec.

### Test vectors

The `audio_frames` section of `testdata/protocol-vectors.json` (see the paragraph under §7) holds
the key derivation (`info`, `transmission_key`) and complete frames for a sender-talks and an
answerer-talks transmission (the same `transmission_id`, different talkers, different keys);
`reject` cases for each failure reason of §12.5 and for tampering, a wrong talker, a wrong session
key and truncation; `replay` scenarios for one transmission (verdicts `ok`, `replay`, `drop`); and
`sessions`, stateful scenarios across floor events: grant, release, rejoin snapshot (rule 4),
refused repeats, a receiver reconnect with a suspended transmission (resumed, or treated as
released by a later grant) and the same `seq` under a new transmission id (rule 5).
